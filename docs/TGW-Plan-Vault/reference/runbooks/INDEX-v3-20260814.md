## Shared rules

1. Plan approval covers its declared implementation-through-install phases; do not
   ask for repeated ceremonial approvals.
2. A reviewed candidate is immutable. A fix creates a successor commit and another
   review of the resulting exact identity.
3. Source commits, release selection, wheel activation, Nix activation, durable-data
   reconciliation, and provider effects are separate transitions.
4. Provider or data-only work gets a receipt, not a fake source commit.
5. `main` is fast-forward only. `production` moves only after live acceptance.
6. Dirty or untracked work is reconciled and preserved before cleanup; it is never
   erased because another branch appears newer.
7. Historical refs/worktrees are retired only after preservation, remote readback,
   zero stale consumers, and operator acceptance.
8. Review independence is policy-driven and harness-neutral; production may require
   human release approval without hard-coding human-only review into every profile.
9. Coding membership and production-install privileges should remain separate,
   least-privilege capabilities. Neither grants eBay/provider authority.
10. Never claim installation from Git state alone; verify the selected release,
    executing runtime, services, and user-visible behavior.

## Where to start

- A production code bug or patch: start with the
  [remediation commit strategy](remediation-commit-strategy-v1-20260814.md), then use
  the governed coding/release and installation runbooks.
- A provider/data discrepancy with no code change: use the domain reconciliation
  procedure and persist its receipt; do not create a source commit.
- A host/service incident: use day-two platform operations.
- A Nix/module change: use Nix flake maintenance.
- An item workflow failure: use listing workflow operation and recovery.
