## Background — What Went Wrong

For approximately one month, TGW operated without any eBay listing data in the local dataset.
Despite regular requests to address it, the gap was not formally identified as a blocking problem
until 2026-06-17, when PP-DATA-OWN-001 was opened and a bulk Inventory API pull was run.

During that blind period several compounding problems occurred:

1. **Shipping pricing unknown** — migrated from legacy to Inventory API without capturing
   fulfillment policy data per listing; now cannot verify which shipping profile is applied to
   which listing without a new API pull.
2. **Photo worker renamed primary photos** — `tgw alt-text` renamed `<SKU>.jpg` → `<SKU>-alt.jpg`
   on 619 items, displacing the first photo from its correct position. Code fix committed
   (9319e5e), damage not yet repaired.
3. **False regression incident** — a cross-reference audit on 2026-06-16 falsely concluded that
   web UI code had been lost. No code was actually lost (PP-RECOVERY-001). The real gaps (eBay
   data, shipping) were already present and unrelated to the audit false alarm.
4. **Dev environment confusion** — work was on an unmerged task branch during the false-regression
   incident; PP-RECOVERY-001 directed a merge that still has not happened.

## Section 3: Photo Disaster (ISS-013)

**619 items** have their primary photo corrupted.

**What happened:** `tgw alt-text <sku>` was intended to generate AI alt-text and store it as
a companion file `<SKU>-alt.jpg`. Instead it renamed the original `<SKU>.jpg` to `<SKU>-alt.jpg`,
making the alt-text variant the only file, named incorrectly, in the wrong sequence position.

**Current state:**
- 619 items: `<SKU>-alt.jpg` exists, `<SKU>.jpg` does not exist
- These items display a wrong/random photo first in the gallery and on eBay
- Code fix committed (9319e5e — copy not rename); no new damage is occurring
- `photo_history_recovery.py` exists on disk for repair but is not deployed

**Recovery options:**
1. Rename `<SKU>-alt.jpg` back to `<SKU>.jpg` for affected items (loses alt-text content)
2. Pull the original primary photo from eBay's stored imageUrls (in `ebay_live.inventory_item.product.imageUrls`) and save as `<SKU>.jpg`, keep `<SKU>-alt.jpg` as companion
3. Run `photo_history_recovery.py` if it implements the correct repair logic

Option 2 is cleanest — eBay has the original photos stored and `ebay_live` now has the URLs.

## Lessons for Process Recovery

### Why the eBay data gap persisted

- eBay data needs were raised in conversation but never converted to a **blocking todo**
  in the canonical task queue (`tgw todo`). Work proceeded on features that assumed eBay data
  was present, but no one checked the precondition.
- The plan had `ebay_sync` running, which gave false confidence — but `ebay_sync` wrote to
  `ebay_listing` (a synthesized summary block), not to `ebay_live` (the raw API mirror).
- PP-DATA-OWN-001 was not opened until 2026-06-17; all prior work that needed eBay data
  (repricer, offers UI, revision UI) was built against a non-existent data source.

### How to prevent recurrence

1. **Gate feature work on data preconditions.** Before building a feature, add a todo that
   verifies the required data exists for ≥1 real item. If it doesn't, that becomes the first todo.
2. **Run `tgw catalog-verify` before each session.** It surfaces data quality issues that
   conversation doesn't.
3. **PP-DATA-OWN-001 Phase 2 (ongoing sync) is the fix** — `ebay_live` must stay current
   automatically. Until that runs on a schedule, `ebay-pull` must be run manually before
   any session that touches listing data.
4. **Perplexity verification** — before committing to a design that depends on external APIs,
   run a deep-research verification prompt (see companion doc) to confirm the API returns
   what you expect and that the design survives the edge cases.
