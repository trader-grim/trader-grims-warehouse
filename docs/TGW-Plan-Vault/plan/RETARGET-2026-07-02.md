## Diagnosis — five fragile points (with evidence)

### F1. "Code complete" is treated as done; nothing forces live verification

The gap between *built* and *integrated into daily use* is exactly the gap between
"tests pass" and "Dave used it on a real item."

Evidence:
- PP-LISTEDITOR-001 Phase 2: CODE COMPLETE session 40, live-fire still not done two
  sessions later.
- PP-ACTIONCONSOLE-001: built session 40, operator test still pending.
- Session 41's worst bugs were all invisible to the 563-test suite because they only
  exist at runtime: price-reducer writes silently dropped, aspect-fill text-only
  despite photos being available, timestamps wrong at 13 display sites, permission
  drift reverting files within minutes of being fixed.
- The first real end-to-end listing attempt (the whole point of the system) is what
  exposed all of this — meaning the *first user* of most features is Dave, in
  production, under time pressure.

**Root cause:** the definition of done stops at "tests pass + committed." There is no
mandatory step where the feature is exercised on a real item and the actual observable
result (listing on eBay, JSON on disk, row in the ledger) is inspected.

### F2. Nothing watches the system between sessions

Issues become emergencies because the interval between "starts failing" and "someone
looks" is unbounded.

Evidence:
- `tgw-clipd` restarted **15,769 times** before anyone noticed.
- `pm_intake` failed every write for ~19–24 hours (60 PermissionErrors) silently.
- 3,134 `ebay_draft` dead-letters accumulated from an exhausted OpenRouter account.
- `tgw health` currently red on backups/nats/ebay_sync_fallback — and has been, and
  only a human running it by hand would know.
- Three separate eBay quota pools were exhausted before the drains were found.

**Root cause:** `tgw health`, dead-letter counts, restart counters, and quota state
all exist as *pull* information. Nothing pushes a delta to Dave. The self-healing
philosophy ([[feedback-self-healing-system]]) is applied per-incident but has no
platform expression yet.

### F3. The plan corpus has outgrown every context window — including the humans'

Evidence:
- `TGW-Master-Plan.md` is **6,060 lines**, mixing settled architecture, 30 PP designs
  (several complete, several frozen), embedded shell transcripts, and session history.
- `handoff.md` is v5 (2026-06-12 base) with session logs appended out of order
  (32, 34, 33, 32-again, 41) and duplicated section numbers; its "risky" list still
  headlines an Antigravity deadline that expired two weeks ago.
- 9 sync-conflict copies of the master plan sit in `plan/`; the inbox `queued/` holds
  6 unprocessed session notes.
- Session startup asks a model to read all of this before doing anything — so every
  session spends a large share of its budget (and attention) re-deriving context, and
  the work itself gets the degraded remainder. This is the direct mechanism behind
  "models overwhelmed" and behind quality slips like the session-39 silent
  substitutions.

**Root cause:** one file accretes everything; nothing is ever moved out. The plan is
optimized for completeness, not for loading.

### F4. Too many open fronts; WIP never drains

Evidence:
- 30 PP-* items tracked; recent sessions touched eBay pipeline, NixOS, Sway, Flutter,
  clipboard, lan-mouse, KDE Connect, backup, and permissions — often several in one
  session.
- Session 41 was "extremely long," found enormous amounts, and still ended with the
  core live-fire tests (listeditor apply, action console) unexecuted.
- Meanwhile PP-BACKUP-001 — ranked risk #1 in the handoff for weeks — still has no
  timer running, because its operator chunks are large and vague and always lose to
  whatever is on fire.

**Root cause:** no explicit WIP limit and no single named "critical path." Everything
is important, so urgency is decided by whatever broke most recently.

### F5. Spec fidelity fails silently under context pressure

Evidence: session 39 shipped "every 6h" for Dave's "once daily before reset" and a
30-day cache TTL Dave never asked for — both silent, both caused real quota
exhaustion, both found only by transcript archaeology in session 41. Already
memorialized ([[feedback-implement-as-specified]]), but a memory is advice; it needs a
structural home.

**Root cause:** large, multi-goal work orders with implicit acceptance criteria. The
bigger the chunk, the more the model fills gaps with its own defaults.

## The work-packet format (the "small chunks" mechanism)

One packet = one todo = one model session (or less). A packet is issued as
`tgw todo --add` text plus, for anything non-trivial, a file
`plan/packets/<todo-id>-<slug>.md`:

```
# Packet: <one-line goal, stated as an observable outcome>
Todo: #NNNN   PP: PP-XXX-001   Track: R1.x
## Context budget (ALL the model may load)
- plan core (≤500 lines) + this packet
- reference doc(s): <specific file(s), not "the reference library">
- code: <specific paths>
## Spec
<what to build/change — explicit on cadence, TTLs, limits, defaults.
 Anything unstated is NOT delegated: if the model must choose, it must
 flag the choice in its report, per feedback-implement-as-specified.>
## Out of scope
<the adjacent things it will be tempted to also fix — name them>
## Acceptance (live)
<the command/URL/SKU that proves it works on real data, and what Dave
 or the model must observe. "Tests pass" is necessary, never sufficient.>
## Quota/risk note
<any eBay/LLM API calls this adds or removes — per feedback-api-quota-flagging>
```

Sizing rule of thumb: if the spec section needs more than ~30 lines or touches more
than ~3 files, split it. Small packets are also what makes Aider and cheaper models
usable again (see routing table in `next-process.md`).

## Guidance for Dave — getting effective results from the models

1. **One outcome per session, stated as an observation.** Open with "by the end of
   this session, X is true and you will show me" — e.g. "item Y's price changes on
   eBay via the revision editor." Session 41 covered heroic ground precisely because
   it had no single exit condition; heroic sessions are where integration and
   verification get deferred.

2. **Refuse "code complete."** The phrase means "not done." Ask for the live
   demonstration — the URL, the log lines, the item JSON diff, the eBay screenshot —
   before a todo closes. R3.5 makes this policy, but you enforcing it verbally is
   what makes it real.

3. **Issue packets, not themes.** "Fix the quota drains" produced three sessions of
   archaeology; "cap the 25707 fallback to once per 24h, here's the file" takes
   twenty minutes. The packet template's *Out of scope* and *Acceptance* sections are
   the two highest-leverage lines you can write — they're where silent substitution
   and scope creep die.

4. **Separate triage from building.** Start the day with the ops digest (R2.1) — ten
   minutes, decide what's on fire — then run build sessions that ignore everything
   not in their packet. Session 41 shows what happens when one session does both:
   the triage was excellent and the building (live-fire tests) got squeezed out.

5. **Match model to packet, and keep contexts cold-startable.** Design/diagnosis and
   anything cross-cutting: Fable/Opus with the full plan. A well-written packet:
   Sonnet or Aider, loading only its context-budget list. If a packet can't be
   executed by a fresh session without oral tradition, the packet (not the model) is
   the problem.

6. **Every live defect buys a detector.** You already run "find the rest of this bug
   class" sweeps (the fence_patch_item audit) — extend the question to "what standing
   check would have caught this in a day?" and make *that* a packet. The price-reducer
   bug's detector is a draft-vs-live price reconciliation in `ebay_sync`; clipd's is
   R2.4. Patches fix yesterday; detectors fix next quarter.

7. **Guard your approval bandwidth.** The human-only gates (publish, scopes, bulk
   ops) are correct, but big vague operator todos rot (#61 has been risk-#1 for
   weeks). Anything assigned to you should be ≤15 minutes with exact commands — R2.5
   is the template.

Dave's clarification: the testing lag is not scheduling — the Taxonomy exhaustion has
physically blocked operator testing for two days. Dev/test must never again be hostage
to a metered API. The repeated "stupid mistake" has a single class: **unbounded
background consumption of a metered API**. The invariant to assert (resimplify

**Timestamp reconciliation finding (verified live 2026-07-02):** no stored data is
corrupted. `queue_jobs` timestamp columns are all `timestamptz` (Postgres stores UTC
internally; the GMT session zone only affects rendering), and journald stores UTC
internally and renders system-local (host tz is America/Los_Angeles — the clock itself
is correct). The "7 hours in the future" incident was rendering-only, already fixed at
all 13 sites. To correlate historical logs across surfaces, view everything in one
zone: `journalctl --utc` beside raw ISO+00:00 values. The only genuinely ambiguous
writes are whatever the 6 naive call sites produced — R0.5 classifies those. Note the
quota-reset gate in `ebay_sync.py` uses explicit `ZoneInfo("America/Los_Angeles")`,
so it does not depend on the host clock setting.

**Priority change:** R2 (self-diagnosis) is no longer parallel — R0.1/R0.2 + R2.1
(digest) come before any further feature build. Dave: "despite requesting we log so we
can self-repair, there is no self-diagnosis happening" — confirmed correct; logging
exists, but nothing reads it on his behalf.
