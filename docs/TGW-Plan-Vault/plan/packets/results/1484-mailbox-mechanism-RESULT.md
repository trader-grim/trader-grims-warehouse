Deviations from spec:
- The PP doc's illustrative filename shape was `MSG-<ts>-from-<sender>.md`;
  implemented instead as `<FROM-ACTOR>-<TYPE>-<slug>-<date>.md` to exactly
  match the real, already-live naming convention found in
  `inbox/claude/` and `inbox/tigwa/` (e.g. `CLAUDE-REQUEST-...`,
  `TIGWA-REQUEST-...`, `RESPONSE-...`) — the packet's own instruction was to
  "follow the existing naming convention you should reverse-engineer from
  real examples," which takes precedence over the PP doc's earlier, more
  abstract sketch of the same idea. Flagging explicitly since it's a literal
  reading of one part of the spec (PP doc) vs. a more specific instruction
  in the todo body/dispatch — resolved in favor of the more specific, more
  recently-stated instruction.
- `to_actor` validation: a message to a brand-new actor name that doesn't
  already have an `inbox/<actor>/` directory and isn't one of the three
  known actors (claude/tigwa/dave) is REJECTED with guidance, not silently
  auto-created. The PP doc says the design should be "extended to any new
  addressable actor as one gets added" — read this as "the mechanism must
  not gatekeep a deliberately-added new actor," not as "the CLI should
  silently create a mailbox directory for any typo'd string," which risks
  orphan directories (a system-wide project rule: "no orphan objects").
  Once the directory exists (a one-time, deliberate step), sends succeed
  normally. Flagging as a judgment call since the packet didn't specify
  which reading was intended.
- MCP tool's `from_actor` default is `'tigwa'` (not `'claude'` like the
  CLI's default) — the MCP front door is explicitly for "agents that don't
  have shell access" per the packet, i.e. Tigwa/Hermes-based actors, not
  Claude Code (which has the CLI/skill). Flagging since this is an
  unstated default choice, not literally in the spec.
- Added `TGW_HOOK_REPO_ROOT` env var override (defaulting to the existing
  hardcoded `/opt/TGW/src/trader-grims-warehouse` path) purely to make the
  hook's behavior offline-testable without coupling to live Plan Vault
  content that changes daily. Not in the packet's explicit ask but needed
  to satisfy the "acceptance: pytest -q must pass offline... new behavior
  gets tests" constraint without a flaky/non-deterministic test.
